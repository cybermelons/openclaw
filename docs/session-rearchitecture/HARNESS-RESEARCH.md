# Harness Session-Management Research vs. Our Re-Architecture Plan

Date: 2026-08-26. Method: web search + primary-source fetch (docs, source-derived wikis, GitHub issues). Compared against `tmp_plan-session-rearchitecture.md` (P1-P5) and `tmp_report-ponytail-session-audit.md`.

Confidence key: **[H]** high (primary doc/source), **[M]** medium (source-derived wiki/summary, unverified against raw code), **[L]** low (blog/inference, flagged explicitly).

## 1. Per-harness findings

### Claude Code (Anthropic)

- **Substrate [H]**: per-project transcript files on disk, one file per session, continuously appended as you work. Docs: `~/.local/share/claude/sessions/session-<id>.json`-style layout (per an SDK-adjacent doc [M]); official docs describe "local transcript files" without giving exact schema. Source: https://code.claude.com/docs/en/sessions
- **Resume [H]**: `claude --continue` (most recent in cwd), `claude --resume <id|name>` (exact or picker), `/resume` in-session. Resume restores: full history, model (with fallback rules), agent, permission mode (with plan/bypass exceptions), active goal, non-expired scheduled tasks. Cross-directory resume does an ID search across all projects on the machine, disambiguated only when exactly one project has messages for that ID — a hand-copied duplicate causes a "not found" rather than an arbitrary resume (explicit anti-ambiguity design). Not restored: `--mcp-config`, `--settings`, `--plugin-dir`, `--fallback-model`, dynamically-added dirs.
- **Concurrency [H, negative example]**: multiple live GitHub issues describe **exactly the failure class our plan targets** — concurrent-writer corruption with no CAS/locking on the shared config file `~/.claude.json` (distinct from per-session transcripts):
  - #29003 "corruption from concurrent instances on same machine" — mid-write truncation, an auto-recovery system detects corruption and restores from backup, but restores stale data (feature flags) → https://github.com/anthropics/claude-code/issues/29003
  - #29036 "Race condition ... loses all session settings" — "concurrent writes without file locking" resets the file to a minimal stub → https://github.com/anthropics/claude-code/issues/29036
  - #29217 "corrupted by concurrent writes from multiple sessions" — truncated mid-write, `Unexpected EOF` → https://github.com/anthropics/claude-code/issues/29217
  - #18998 "Severe corruption in multi-project environments (30+ concurrent sessions)" — 14+ corruptions in 11 hours at scale → https://github.com/anthropics/claude-code/issues/18998
  - #32160 "Corrupted session file causes unrecoverable crash loop" — VS Code extension auto-resumes the last (corrupt) session every restart with no escape hatch except manual file rename → https://github.com/anthropics/claude-code/issues/32160
- **Notes**: Anthropic's own docs concede session resume is best-effort in places (e.g. `Failed to resume the conversation` error path is documented, not eliminated). The **auto-recovery-from-backup** pattern (detect corruption → back up bad file → restore last good) is a real mitigating design worth citing, but it is reactive, not preventive — it exists because there is no write-serialization/CAS layer, which is the same root cause our plan calls out for our own `session_nodes` divergence bugs.

### OpenAI Codex CLI

- **Substrate [H]**: JSONL "rollout" files, one file per session, append-only, one JSON object per line with a monotonic `seq` field. Path pattern `~/.codex/sessions/rollout-<timestamp>-<uuid>.jsonl`. Source (source-derived, cites `codex-rs/core/src/rollout/recorder.rs`): https://artvandelay.github.io/codex-agentic-patterns/learning-material/18-rollout-system/
- **Resume [H/M]**: `codex resume <rollout-file>` reads the file, parses every line, and reconstructs `ConversationHistory` (a `Vec<ResponseItem>`) in order — a pure replay, no separate durable "resume marker"; ordering guarantee comes from **file-append order** (`seq` is a monotonic tag baked in at write time, matching physical line order). DeepWiki (source-derived) describes a `ThreadManager` opening the rollout file and reconstructing state via `ResumedHistory` on resume — consistent with the direct recorder description. Source: https://deepwiki.com/openai/codex/4.4-session-resumption-and-forking (title-only fetch; corroborated by the recorder doc above)
- **Concurrency [H]**: effectively **single-writer per file, no CAS** — the recorder pattern (`RolloutRecorder` holds a `Sender<RolloutCmd>` channel, single background task appends and flushes) means one writer task owns the file; there is no documented multi-writer merge story because the format assumes one process, one file, one writer. This is a _design choice_, not a gap: it sidesteps concurrent-write conflicts entirely by construction rather than solving them.
- **Known bug class [H]**: file permissions, not concurrency — rollout files were created world-readable (`0644`) on Unix while the separate `history.jsonl` was correctly `0600`, letting any local user read another user's full transcript. Fixed as a permissions bug, unrelated to the storage model itself. Source: https://github.com/openai/codex/issues/21660
- **Notes**: An open community discussion also shows people scripting `pipx install codex-rescue` / `codex-rescue doctor --latest` — a third-party tool built specifically to diagnose "interrupted or damaged Codex CLI sessions," and its own description says it "does not automatically replay unknown side effects" — implicit admission that some interrupted sessions are not cleanly resumable and manual repair is a known enough problem to have spawned tooling. Source: https://github.com/openai/codex/discussions/1076

### Cursor

- **Substrate/Resume/Concurrency [L]**: no primary Cursor engineering doc surfaced describing internal background-agent session storage schema. Search results were dominated by third-party "memory" plugin products (Create State, Conare, Hindsight) layered on top of Cursor, not Cursor's own architecture. One relevant first-party-adjacent data point: Cursor's **Privacy Mode** guarantee states "no prompts, completions, or file content are stored server-side beyond the duration of the request," and explicitly notes the trade-off that "some features that depend on cached state (like resuming a long Composer [session]) ..." are degraded under that mode — implying Cursor's resumable session state is normally server-cached, not purely local. Source (secondary, DeployHQ guide, not Cursor's own docs) [L]: https://www.deployhq.com/guides/cursor
- Cursor's own "Automations" (shipped ~March 2026 per secondary source) add a Memories tool so scheduled/event-triggered agents "learn across runs," described as "a standalone configuration rather than a node in a platform-level event bus" [L]: https://www.augmentcode.com/tools/cursor-background-agents-vs-cosmos
- **Verdict**: insufficient primary-source evidence to make firm claims about Cursor's session persistence internals. Flagged low-confidence; excluded from the comparison table below except as a gap note.

### Goose (Block)

- **Substrate [H]**: SQLite database, `{data_dir}/sessions/sessions.db`, accessed via `sqlx`, **WAL journal mode**. Source (source-derived sandbox/security analysis referencing actual code paths, e.g. `crates/goose-mcp/src/computercontroller/platform/macos.rs:9`): https://agent-safehouse.dev/docs/agent-investigations/goose
- Each session stores: conversation history, token usage, working directory, associated recipes, provider metadata, extension state — i.e., session record is a **rich single row/object**, not just a message log. Source (DeepWiki, source-derived): https://deepwiki.com/block/goose/4.3-session-management (title-only fetch, corroborated by the safehouse doc)
- **Resume [M]**: implied by "every conversation ... is backed by a persistent session" plus stored working-directory/provider-metadata/extension-state — resume rehydrates the full session context, not just chat text. No explicit description found of a resume-ordering guarantee (e.g., whether it's transaction-committed vs. best-effort).
- **Concurrency [M, generic SQLite WAL properties, not Goose-specific]**: WAL mode inherently gives **one writer at a time**, readers don't block the writer, and crash recovery replays the WAL back into the main DB file — SQLite's own docs: https://www.sqlite.org/wal.html. This is a structurally stronger baseline than flat-file-with-no-lock (see Claude Code's `.claude.json` bug class above), but it's SQLite's off-the-shelf guarantee, not a bespoke CAS/revision scheme — no evidence Goose adds its own optimistic-concurrency layer on top.
- **Notes**: no Goose-specific published bug-class writeup on session consistency was found; the single-writer WAL model likely just avoids the whole class of "two writers stomp the same file" bugs the Claude Code issues show, for free.

### Aider

- **Substrate [H]**: flat files, not a database. `.aider.chat.history.md` (markdown transcript log), `.aider.input.history` (input history, configurable via `--chat-input-history-file`), and a separately-computed, non-persisted "repo map" (rebuilt each turn from `git` state + ctags-like analysis, not stored as a session artifact). Source: https://aider.chat/docs/faq.html, https://aider.chat/docs/repomap.html
- **Resume [H]**: no formal "session" object at all — the "session" _is_ the chat history markdown file, which can be shared via gist and rendered at `aider.chat/share/?mdurl=...`. There's no `resume <id>` command; continuity across restarts is whatever files remain on disk in that directory. This is the simplest model in the survey: **no session store, just append-to-markdown + re-derive repo map fresh each run.**
- **Concurrency [H]**: explicitly single-user, single-repo, single-writer by design — the FAQ states "aider can only work with one repo at a time" and that editing files yourself while aider is running risks conflicting with aider's own edits ("Your edits and aider's edits might conflict" — user is warned, not protected). No CAS, no lock — pure best-effort, "don't do that."
- **Notes**: Aider reads "the latest copy of files from the file system when you send each message" — i.e., no cached/stale-file problem because there is no cache; it always re-reads. This sidesteps an entire category of staleness bug at the cost of doing zero speculative optimization.

### Amp (Sourcegraph)

- **Substrate [M]**: "Threads are persistent conversations that maintain context across interactions" — by default stored server-side at Sourcegraph (ampcode.com/threads), with local settings/config separate. Sources: https://github.com/sourcegraph/amp-examples-and-guides/blob/main/guides/cli/README.md, https://zoltanbourne.substack.com/p/early-preview-of-amp-the-new-ai-coding (secondary but consistent)
- **Resume/forking [M]**: "Amp can fork existing threads and use the original thread as context in a new thread" — fork-based branching, similar in spirit to Claude Code's `/branch`/`--fork-session`, but server-hosted. Source: https://github.com/ampcode/amp-examples-and-guides/blob/main/guides/context-management/Context%20Engineering%20-%20Amp.md
- **Concurrency [L]**: no primary doc found describing conflict resolution for concurrent edits to the same thread; Amp's newer "orbs" model (per Sourcegraph's own product page) gives each thread/task its own isolated sandboxed environment — "no worktrees to juggle, no port conflicts" — which sidesteps _file-level_ concurrency by giving each thread its own execution environment, but says nothing about the thread-metadata store itself. Source: https://sourcegraph.com/amp
- **Notes**: because threads are server-authoritative, Amp likely inherits whatever a real backend DB gives it (transactions, single source of truth) rather than a client-side sync/merge problem — but this is inferred from product framing, not a published architecture doc. Flagged **[L]** for the concurrency claim specifically.

## 3. What to steal (ranked, concrete)

1. **Append-and-flush-before-ack as the cheapest possible "ordering by commit" primitive (from Codex).** Where our plan proposes heavier machinery (resume_epoch commit, drain-before-dispatch transaction) for narrow log-like satellite writes (e.g., progress/history append paths that are naturally sequential, single-writer within a turn), consider whether a plain synchronous-append-then-flush suffices instead of building epoch/CAS scaffolding for that specific writer. Reserve the heavy revision-CAS machinery (P1) for the genuinely multi-writer surfaces (session_nodes core entry, satellites with concurrent writers) where Codex's assumption (one writer, one file) doesn't hold for us.
2. **Detect-corruption-then-restore-from-backup as a last-resort safety net (from Claude Code's own mitigation for `.claude.json`).** Even with P1's CAS in place, it's cheap insurance to keep an automatic "last known good" snapshot + integrity check at DB-open time, so a bug that slips past CAS (bad migration, disk corruption) has a documented recovery path rather than a crash loop — note Claude Code's own #32160 shows what happens _without_ an escape hatch: an auto-resume-on-corrupt-session crash loop with no way out except manual file surgery. Any equivalent auto-resume-on-boot behavior in our system should have a "corrupt-marker → skip/quarantine, don't crash-loop" fallback.
3. **Always-re-read-fresh-state as a staleness killer (from Aider).** Aider sidesteps stale-cache bugs entirely by never caching — it re-reads files from disk every turn. Our plan already treats columns as indexes-not-truth (P2), which is the schema-level analogue; worth an explicit check during Phase 2/3 implementation that no code path caches a _projected entry_ across a turn boundary the way the old "cache layer's fifth shape" did (ponytail finding referenced in the plan) — Aider's zero-cache posture is the discipline check for "did we actually kill every stale-read path," not a new technique to add.
4. **Self-contained event records (from Codex's rollout lines) as a lint-fence discipline note for P3's projection pipeline.** Codex's design principle "each line has complete context, never partial" is a good acceptance test for our one-projection-pipeline goal: after Phase 2, a corrupt/partial `session_entry_json` blob should never require cross-referencing other rows to determine validity — should already be true given `SessionRowCorruptError` in the plan, but worth stating as an explicit test case.

## 4. What our plan over-builds (if anything)

- **P4 (satellite contracts) may be scoped larger than the field's simplest examples justify for some satellites.** Codex/Aider/most of the field don't have satellite tables at all because they don't need multi-writer coexistence; Goose bundles everything into one record. Our plan is right to keep participants/read-receipts/progress separate (that's an existing, correct instinct per the plan's own text), but the "own revision or last-write-wins, declared in one contract file" ceremony should be sized per-satellite: a satellite with genuinely one writer (e.g., progress cards written only by the owning turn) doesn't need the same contract weight as one with concurrent fire-and-forget writers (participants). The plan doesn't currently say this explicitly — worth a one-line addition distinguishing "single-writer satellites: last-write-wins is sufficient, skip revision" vs. "multi-writer satellites: need the full contract."
- **Phase 6's admission fence via DB lease row** is more machinery (a lease row keyed by process generation) than any surveyed harness uses — but this is because none of them coordinate two live process generations during a hot-reload/restart the way this system apparently does (`session-lifecycle-admission.ts` chunk-skew hazard). No harness in the survey has an equivalent "two versions of my own server negotiating a handoff" problem, so there's no simpler proven pattern to borrow — this genuinely looks like novel-to-us complexity, not gold-plating. Flagged as _not_ over-built, but worth double-checking against real blast radius before landing (matches the plan's own ordering rationale — "6 last, highest blast radius").
- **No evidence any harness formalizes a five-phase migration with a dedicated characterization-test wall (Phase 0) before starting.** This is heavier process than typical OSS practice (most of these projects seem to evolve their storage format via ordinary PRs) — but that is a two-sided finding: the field's lack of a formal safety-net phase is exactly why bugs like the Claude Code `.claude.json` corruption issues linger unfixed for what appear to be many months across multiple duplicate reports (#29003, #29036, #29217, #18998 — four separate issues for one root cause). Phase 0 is not over-building; if anything it's the harness field's absent step.
